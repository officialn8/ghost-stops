# Ghost Stops Project Review — Feb 1, 2026

Scope: Full docs review + codebase review via focused audits (go-etl pipeline, frontend data validity, frontend UI/UX). This document summarizes what is fully working today, what is missing, what could be improved, and whether the UI is at Awwwards/Dribbble caliber.

## What Is Completed and Fully Working (as of today)

Based on docs and code review, these appear implemented and operational when data is present and sync has run:

- Chicago CTA pipeline structure: GTFS ingest, Socrata ridership sync, compute metrics, and API exposure.
- Multi-model schema for CTA: `Station`, `RidershipDaily`, `StationMetrics`, `StationAlias`, and facts/narrative tables.
- Hybrid sync architecture (local cache of recent ridership + Socrata source of truth).
- Ghost score concept, computed from rolling averages and surfaced in API and UI.
- Missing-data semantics: a `dataStatus` field exists and UI uses neutral display for missing data.
- Station mapping improvements: alias table + normalization + enhanced matching logic in Go ETL.
- ETL parsing + sync safety: shared date/ride parsing, invalid-row logging, transactional upsert+prune.
- GTFS line mapping via routes/trips/stop_times with fallback to stop_desc.
- Backfill ridership CLI for historical pulls without pruning.
- Frontend/API safety: response validation, safe JSON parsing, and normalized `dataStatus`.
- Narrative system scaffolding (types, renderer, archetypes, components, API response shape).
- Premium design system foundations: tokens, glass effect, and several themed UI components.
- Mobile UI framework in place: bottom sheet, layout, and mobile detail components exist.

## What Is Missing or Incomplete

### Data & Narrative System
- Facts data in `scripts/data/top25-facts.json` is placeholder; not real or validated.
- Phase 2 automated facts pipeline is planned but not implemented (Census, LODES, FHWA, historical CTA).
- Data freshness monitoring and automated alerts are not implemented.

### ETL Robustness
- GTFS line extraction now uses GTFS routes/trips/stop_times; fallback still relies on `stop_desc`.
- Sync runs are transactional for upsert + prune; partial runs no longer prune.
- Multiple normalization/matching pathways exist, creating drift and mismatches.
- Tie-break handling exists; fuzzy matching is still missing.

### Frontend Data Integrity
- API response validation is present in core fetch paths, but not global.
- Division-by-zero and null handling have been hardened in `/api/chicago/stations/[id]`.
- JSON parsing of `lines` is safe in API and map layers.
- `dataStatus` handling is normalized across main UI surfaces.

### UI/UX
- Motion choreography and micro-interactions are present but not consistently premium.
- Visual hierarchy and spacing rhythm are uneven across key panels.
- Typography system is present but not applied consistently across components.
- Skeleton/loading states are basic and not yet premium.
- No dark mode implementation (docs mention it as a backlog item).

## Is the UI Awwwards/Dribbble Winning?

**Verdict: Not yet.**  
The design system direction is strong and the ghost-themed glass language is compelling, but the execution lacks the refined motion choreography, depth layering, and typographic discipline expected at award-winning levels. The UI is portfolio-grade in concept, but not yet in polish.

### Why it falls short today
- Motion feels mechanical, not choreographed (panels/lists/hero do not feel staged).
- Spacing and hierarchy are inconsistent, which undermines perceived quality.
- Micro-interactions are basic; the interface does not feel “alive.”
- Loading and empty states are still MVP-level.
- Data visualizations are not yet premium (or fully consistent).

### What would make UI/UX developers jealous
Top improvements that would push the experience into Awwwards/Dribbble territory:

1. **Motion orchestration and shared element transitions**  
   Panel entrances, card-to-detail transitions, and ghost score animations should be staged and cohesive.

2. **Multi-layer depth system**  
   Add an elevation token system, layered shadows, subtle gradients, and noise textures.

3. **Typography discipline**  
   Enforce consistent type scale + line-height rhythm across list, detail, and story sections.

4. **Micro-interactions**  
   Add magnetic hovers, ripple/touch feedback, and spring-based press states.

5. **Premium loading states**  
   Replace generic skeletons with tailored, animated placeholders for lists and details.

6. **Chart polish**  
   Make the ridership chart a hero moment (animated area chart, tooltip polish, gradient fill).

## ETL Logic Soundness and Data Accuracy

**Overall:** The pipeline is functional but has correctness and robustness risks that can impact data accuracy.

### Key soundness risks (Go ETL)
- **Silent data loss in ridership parsing**: resolved (invalid rows logged + skipped).
- **Date parsing fragility**: resolved (shared parser with multiple formats).
- **Line extraction fragility**: mitigated with GTFS route/trip mapping; fallback remains.
- **Variance calculation likely incorrect**: resolved (per-station variance).
- **Ambiguous station matching**: mitigated with tie-breakers + ambiguity logging.
- **Pruning risk on partial sync**: resolved (transactional sync).

### Confirming “right data”
These checks should be run to assert data accuracy:

- Validate station coverage: `COUNT(DISTINCT stationId)` in last 365 days ≈ 143.
- Inspect unmatched station names file and reconcile new mismatches.
- Verify `dataStatus` logic: missing stations are not treated as zero-ridership.
- Verify date window retention: oldest `serviceDate` is within 365 days of max date.
- Run a sanity range check on ridership values (no negative, no extreme outliers).
- Confirm `ctaStationId` mappings against official CTA station list.

## Could We Be Pulling More Data?

Yes — the current MVP only pulls daily entries for rail stations and GTFS metadata. High‑value data sources to consider:

- **CTA Train Tracker API** for real-time arrivals and reliability context.
- **Service alerts** (CTA feed) to correlate ghostiness with disruptions.
- **Historical CTA ridership** beyond 365 days to show trends and recoveries.
- **Census + LODES + FHWA** for narrative facts (planned, not implemented).
- **Bus ridership and stops** to contextualize nearby alternatives.
- **Station accessibility + ADA** data to explain low usage in some stations.

## Where Analysis May Be Wrong or Overconfident

These are the biggest analysis risks today:

- **Ghost score without context**: rolling 30‑day average alone can misclassify seasonal or disrupted stations.
- **Missing vs zero confusion**: any mislabeling skews rankings and map color encoding.
- **Station matching ambiguity**: subtle naming collisions can misattribute ridership to the wrong station.
- **Terminal/transfer weighting assumptions**: static assumptions can distort scores.
- **Facts narrative**: placeholder facts are presented as real unless clearly labeled.

## Over‑Complication vs Under‑Investment

### Over‑Complicated Today
- **Multiple normalization pathways** in ETL (harder to reason about correctness).
- **Hardcoded terminal station list** (should be derived from GTFS).
- **Dual matching systems** (sync vs ridership) with inconsistent rules.

### Under‑Invested Today
- **Data validation and QA checks** (missing guardrails for correctness).
- **Response validation on API** (frontend trusts shape too much).
- **Motion polish + micro-interactions** (UI is close but not yet “wow”).
- **Narrative data quality** (requires real sourcing to be credible).

## Recommendations (Prioritized)

- Fix ridership parsing to avoid silent zero inserts and log invalid rows. ✅
- Normalize date parsing across sync paths; fail loudly on unknown formats. ✅
- Make sync transactional (fetch → upsert → prune) to avoid partial data loss. ✅
- Standardize station matching + normalization logic and log ambiguous matches. ✅
- Add explicit response validation (API and frontend), and handle all `dataStatus` values. ✅

### P1 — Data Completeness
- Replace line extraction with GTFS route/trip‑based mapping. ✅
- Add backfill tooling for historical data. ✅
- Implement basic data QA checks (range checks, outlier detection). ✅

  - Typography scale (display-1/2/3, ui-xl/lg/md/sm/xs) in Tailwind config
  - Border radius scale (ui, panel variants) consistently applied

### P3 — Narrative & Storytelling ✅
- Replace placeholder facts with sourced data (or explicitly label placeholders).
- Automate Phase 2 ingestion to remove manual curation bottleneck (scaffolded).
- Add “data quality” flags to narratives for transparency.

## Final Verdict

The product is conceptually strong, and the system architecture is on the right path. The two blockers to “world‑class” today are **data correctness confidence** and **design execution polish**. Solve those two, and the project can absolutely reach Awwwards‑level impact.
